## 0. 为什么需要这份文档

`doc/开发文档.md` 是一份**比赛文档**——它的目标函数是「10 天内闭合准入条件、拿一等奖」。
在那个目标下，很多决策是对的：写死数据、关键词路由、内存存储、单次演示跑通即可。

但目标换成「知名开源项目」后，同样这些决策全部变成负债。开源项目的目标函数是：

> **一个陌生人 clone 下来，用自己的数据跑一遍，得到的结论是可信的、可复现的、可被质疑的。**

按这个标准重新体检，结论是：**这个项目有一半是真材实料，另一半是精致的演示布景**。
坏消息是布景那一半恰好是对外宣传的核心（AI 分析、视口联动、RAG）；
好消息是真材实料那一半（物理仿真）恰好是别人抄不走的护城河，而且**它能生产真实数据**——
这正是修复另一半的钥匙。

## 2. 现状体检

### 2.1 真实可信的部分（保护好，不要动）

这部分是项目的全部价值来源，重构中要当成资产保全：

| 模块                                         | 为什么可信                                                                            |
| -------------------------------------------- | ------------------------------------------------------------------------------------- |
| `js/slicer.js` 切片引擎                      | 周界偏置 / 扫描线奇偶填充 / Marching Squares 都是真算法，32 项断言                    |
| `js/sim.js` 温控与调平链                     | 一阶滞后热模型；床面误差场 → 9 点探测 → 5×5 拟合 → 双线性插值补偿，数据链自洽且有断言 |
| `js/exporter.js` 导出                        | G-code 的 ΣE 与切片统计守恒是被测试断言的，导出物能进真实切片器                       |
| `js/printers.js` 四机型                      | CoreXY / i3 / Delta 逆解 / 大幅面龙门四套运动学是分别实现的，不是换皮                 |
| `server/lib/http.js` 静态托管                | deny-by-default allowlist + 路径穿越防护，有针对性测试                                |
| **`tests/sim-calib.test.js` 的 stub 打印机** | **能在 node 里无头驱动完整状态机——这是 2.2 节问题的现成解药**                         |

### 2.2 核心问题：三层套娃的假数据闭环 ★

这是整个项目最严重的问题，其他问题都是它的衍生。

**第一层 — 埋结论**（`js/insight-data.js:44-108`）：

```js
var machineFailBase = { "FX-256-01": 0.04, "FX-256-02": 0.06, "FX-256-03": 0.2, "FX-256-04": 0.05 };
//                                                            ^^^^^^^^^^^^^^^^ 直接写死 03 号机故障率 20%
var risky = model.name === "传感器支架" && (material === "ABS" || material === "PETG");
if (risky) pFail += material === "ABS" ? 0.22 : 0.1;        // 直接写死「ABS × 悬垂件」高失败
if (machine === "FX-256-03") reason = r < 0.42 ? "堵料" : r < 0.75 ? "断料" : "热失控";
//                                                                          ^^^ 连故障类型分布都是写死的
var dur = model.baseMin * (0.2 / lh) * speedFactor[material] * ...;
//                        ^^^^^^^^^ 层高与时长的「相关性」是这行公式定义出来的，不是数据里发现的
```

**第二层 — 挖出来**（`js/insight-engine.js`）：分析引擎老老实实把上面埋的东西聚合出来。

**第三层 — 断言挖到了**（`tests/insight.test.js:35 / 81 / 121 / 123`）：

```js
check("故事线：03 号机故障率显著高于 01 号机", m3.failRate > m1.failRate + 0.08, ...);
check("KPI 找到重点机台 FX-256-03", k.worstMachine && k.worstMachine.id === "FX-256-03", ...);
```

**这套测试断言的不是「分析引擎正确」，而是「生成器和分析器用了同一套常量」。**
把 `machineFailBase` 的 0.2 改成 0.02，测试会红——但引擎的正确性一点没变。这是**同义反复，不是验证**。

连带影响：

- `doc/samples/print_jobs_sample.csv`（README 推荐评委/用户一键上传体验的那份）就是这个函数的输出，同样是编的；
- 「层高与打印时长呈显著负相关（r=-0.xx）」这个结论**没有控制混杂因素**——TPU 的 `speedFactor` 是 2.1，材料和层高在生成时独立抽样，算出来的 Pearson r 是被 `0.2/lh` 这行公式直接决定的；
- `D.PRICE`（`js/insight-data.js:18-22`）的材料单价、电价、机时折旧全是无出处常量，注释自称「演示口径」，且**不可从 UI 配置**——但报告里当成钱在算。

### 2.3 「AI 分析」的真相

`js/insight-engine.js:79-97` 是全部的「智能」：

```js
var INTENTS = [
  { id: "machine_fault", kw: ["机台", "哪台", "故障率", "设备", "机器", "保养", "维护"] },
  ... 共 5 条
];
// 命中次数最多的 intent 胜出；一条都不命中 → overview
```

由此产生的具体缺陷：

| 缺陷                                                   | 位置                                                            | 后果                                                                       |
| ------------------------------------------------------ | --------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 5 个桶之外的问题一律降级为「生产概览」                 | `insight-engine.js:90-97`                                       | 「哪种材料最省钱」「周末产能和工作日差多少」→ 答非所问，且不告知用户没听懂 |
| 建议文案是硬编码字符串，与数据强弱无关                 | `insight-engine.js:124-129, 166-172, 204-209, 242-245, 282-286` | 1 次堵料和 100 次堵料给出**一模一样**的整改建议                            |
| **机台排行无最小样本量守卫**                           | `insight-engine.js:107-109`                                     | 只跑过 1 单且失败的机台 → 失败率 100% → 登顶「最需要保养」                 |
| 同一份数据，KPI 卡和分析报告可能给出不同的「重点机台」 | `insight-engine.js:63` 有 `ms.total >= 5`，`:108` 没有          | 界面自相矛盾                                                               |
| 悬垂件对比写死了模型名                                 | `insight-engine.js:152` `r.model_name === "传感器支架"`         | 用户数据里没有这个中文模型名 → 该分析段静默消失                            |
| 无置信区间、无显著性检验                               | 全文件                                                          | 「A 比 B 差」这句话没有任何统计依据                                        |

### 2.4 接上真云端，功能反而更少

`server/services/analysis.js:143-171` 的 `_mapCloudReport()`：

```js
const base = {
  chart: null,          // ← 云端报告永远没有图表
  intent: "cloud",
  ...
};
// 且全程不产生 highlight 字段 → 前端「在 3D 视口中定位」按钮永不出现
```

也就是说：**配好密钥、切到 InfiniSynapse 真实 AI 之后，用户失去图表、失去视口联动（对外宣传的「杀手锏」）、失去结构化数据，只剩几段文字。**
mock 模式反而是功能最全的模式。这个反直觉的降级，是「先做演示、后接真实」留下的最大技术债。

其余云端链路问题：

| 问题                                          | 位置                         | 说明                                                                                                                                                   |
| --------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 整份 CSV 内联进 prompt                        | `services/infini.js:195-208` | token 成本随数据量线性增长；上万行直接超限。应传 schema + 采样 + 聚合结果，而非原始行                                                                  |
| 结构化产物靠「请你输出 JSON」的口头约定       | 同上，第 4 条要求            | 无 schema 校验、无失败重试，解析不出就降级贴纯文本                                                                                                     |
| **后端推送的真实进度事件被前端丢弃**          | `js/insight.js:270`          | `FXApiClient.stream(taskId, function () {}, ...)` — `onEvent` 是空函数。后端辛辛苦苦节流转发的 `reasoning`/`generating` 阶段全丢了，界面只播三步假动画 |
| 单次任务 160–230 秒，无缓存                   | —                            | 同一问题问两次 = 两次真实云端任务 = 双倍成本和等待                                                                                                     |
| 每次提问都重传整个数据集、新建一个 datasource | `js/insight.js:262`          | 问 10 个问题产生 10 份重复数据源                                                                                                                       |

### 2.5 死代码与不实提示

**知识库 / RAG 完全没有接线**：

- `server/services/knowledge.js` 的 `all()` 方法**全仓库无人调用**（已 grep 确认）——文档存进内存、被 TTL 清掉，从未进入任何 prompt；
- 前端**没有任何 UI** 触及 `/api/knowledge`，这个端点在应用里不可达；
- 最严重的是 `server/routes/knowledge.js:13-15`：

```js
note: cfg.mode === "infinisynapse"
  ? "已登记，将在分析任务中注入"      // ← 这句话是假的，没有任何注入逻辑
  : "已登记（演示模式暂存内存；InfiniRAG 接入待附录 B-6 端点核准）",
```

而 `doc/开发文档.md` §3.3 / §5 把「知识库（RAG）」列为四大「集成深度」支柱之一。
**对外宣称的能力 + 对调用方返回的成功提示 + 零实现 = 开源后最容易被截图挂出来的那类问题。**

### 2.6 仿真与分析两半是断的

项目最独特的卖点是「仿真 × 分析融合」，但两半之间只有一根极细的线，而且接错了：

| 断点                 | 位置                           | 说明                                                                                                                                                 |
| -------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **机台 ID 写死**     | `js/insight-data.js:250`       | `machine_id: "FX-256-01"`。切到 FX-500 巨匠跑完一单，采集记录仍写 FX-256-01。`sim.printer.MODEL_TAG` 就在手边没用                                    |

### 2.7 工程与运维缺口

| 项             | 现状                                                                       | 开源后的风险                                                                                                            |
| -------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 持久化         | 数据源 / 任务 / 知识库 / 分享全在 `Map`，TTL 1h（分享 24h）                | 重启即全丢。「24 小时有效的分享页」每次部署都失效                                                                       |

| 可观测性       | 有结构化日志，但无指标 / 无追踪 / 无成本统计                               | 不知道花了多少钱、失败率多少                                                                                            |

## 4. 目标架构

### 4.1 三条不可妥协的设计原则

> **P1 · 可证伪**：任何结论都必须能被追问「样本多少、置信区间多宽、换一份数据还成立吗」。
> 说不出来的结论，宁可输出「样本不足，无法判定」。
>
> **P2 · 来源可溯**：每个数据集带 `provenance`，每份报告带数据来源、行数、时间范围、引擎标识。
> **合成数据在任何界面上都不得伪装成真实数据。**
>
> **P3 · 厂商中立**：InfiniSynapse 是一个 provider，不是架构。
> 换成 OpenAI 兼容端点 / 本地 Ollama / 纯本地统计，应用层零改动。

### 4.2 目标分层

```
┌──────────────────────────────────────────────────────────┐
│ 表现层  3D 视口 · 洞察面板 · 图表（保持零构建可直开的发行物） │
├──────────────────────────────────────────────────────────┤
│ 分析层  question → QueryPlan → 统计核 → 叙述生成            │
│         ├ QueryPlanner   （规则 planner | LLM planner）    │
│         ├ StatsKernel    ★真正的核心：聚合+检验+置信区间     │
│         └ Narrator       （由计算出的事实生成文字，非模板库） │
├──────────────────────────────────────────────────────────┤
│ Provider 层  AnalysisProvider 接口                         │
│         ├ LocalProvider（纯统计，零网络，永远可用）          │
│         ├ InfiniSynapseProvider                            │
│         └ OpenAICompatibleProvider（Ollama / vLLM / 云）    │
├──────────────────────────────────────────────────────────┤
│ 数据层  Dataset(provenance) · Telemetry · 持久化(SQLite)   │
├──────────────────────────────────────────────────────────┤
│ 数据源  ① 虚拟机群仿真（真实物理产出）★                     │
│         ② 用户 CSV  ③ 公开数据集  ④ 标注为合成的生成器       │
└──────────────────────────────────────────────────────────┘
```

**关键洞察**：`tests/sim-calib.test.js` 已经证明**仿真状态机可以在 node 里用 stub 打印机无头运行**。
把它扩展成「虚拟机群」，就能用真实物理过程产出数据——
每台机器有固有的床面误差场、加热器时间常数、送料机构磨损系数，
**失败是从物理过程中涌现的，不是 `pFail = 0.2` 抽出来的**。
这是本项目独一无二的能力：**它是极少数能自己生产真实（而非编造）训练/演示数据的分析工具**。
这一点讲清楚，就是开源社区愿意 star 的理由。

### 4.3 三个关键契约（先定契约，再动代码）

**① 数据集来源标记**

```js
Dataset = {
  id,
  name,
  rows,
  provenance: {
    source: "sim-farm" | "user-upload" | "public-dataset" | "synthetic",
    synthetic: boolean, // true 时 UI 必须显示醒目标记
    generator: { name, version, seed } | null,
    collectedAt,
    rowCount,
    dateRange: [from, to],
    schemaVersion,
  },
};
```

**② 分析报告（本地与云端必须同构 —— 用 JSON Schema 强制，不靠口头约定）**

```js
AnalysisReport = {
  schemaVersion: 1,
  title, verdict,
  confidence: "high" | "medium" | "low" | "insufficient-data",
  sections: [{ h, lines[] }],
  chart: { kind, title, items[] } | null,      // ★云端也必须产出
  highlight: { type, id } | null,              // ★云端也必须产出
  evidence: [{ claim, method, n, statistic, ci95, pValue }],   // ★新增：每条结论的计算依据
  provenance: { datasetId, source, synthetic, rowCount, dateRange },
  engine: { provider, model, taskId, upstreamTaskId, costTokens, elapsedMs },
}
```

`evidence` 是这次重构最重要的新增字段——**它把「AI 说了什么」变成「计算得出什么，怎么算的」**。

**③ Provider 接口**

```js
interface AnalysisProvider {
  id; capabilities: { streaming, structuredOutput, maxRows };
  analyze({ question, dataset, knowledge, onProgress }) -> Promise<AnalysisReport>;
}
```

## 7. 技术选型的取舍说明

几处**建议保留现状**的地方，避免重构过头：

| 现状                     | 是否改           | 理由                                                                                                                           |
| ------------------------ | ---------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **零 npm 运行时依赖**    | **保留**         | 这是真实优势：clone 即起、无供应链风险、审计面小。工业软件用户尤其吃这套。lint/test/build 工具走 devDependencies，不破坏这一点 |
| **`file://` 直开可用**   | **保留为发行物** | 极佳的首次体验。方案：开发期用 ES Module + 构建，发布时同时产出一个 bundled 单文件版本，两者都在 CI 里验证                     |
| **原生 http 而非框架**   | **保留**         | 接口面很薄，`services/*` 已与框架无关。P4 引入 SQLite 时再评估                                                                 |
| **three.js r152**        | **暂缓升级**     | 选型理由（WebGL1 自动回退，兼容老显卡）是真实的、有价值的。先把理由写进文档，再评估 r160+                                      |
| 经典脚本 + `window` 全局 | **要改**         | 这是贡献者门槛的最大来源。P1 起新模块用 ESM，存量按模块渐进迁移                                                                |
| 中文注释                 | **渐进改**       | 不搞大爆炸翻译。新代码英文，UI 文案抽 i18n，存量随重构自然迁移                                                                 |
